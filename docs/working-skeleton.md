# Working Skeleton Approach

A working skeleton means delivering a narrow but complete flow early, then extending it iteratively.

## Why this repo uses it
- Reduces integration risk for a 4-person capstone team.
- Creates stable contracts between backend and future app surfaces.
- Keeps implementation understandable for milestone-driven grading.

## Milestone 1 stopping point
Milestone 1 intentionally stops at **restaurant confirmation** because it validates the core group lunch-decision journey:
1. user identity stub + profile
2. member invite
3. session setup
4. recommendation generation (stub)
5. voting
6. final decision

## Later milestones
- Menu/order/payment simulation
- Owner app behavior
- POS web synchronization behavior
