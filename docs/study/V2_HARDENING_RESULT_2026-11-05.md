# LunchSync v2 구현과 안정성 보완

검증 기준일: 2026-11-05. 기존 `agent/reliability-observability`의 4497c48 및 Gemini가 남긴 미커밋 v2 변경을 이어받았다. 최종 작업은 `codex/lunchsync-v2-hardening`에서 관리한다.

## 사용자에게 달라지는 점

- 점주는 메뉴의 재료·알레르기·조리 시간을 관리하고, 식자재 재고·연결 메뉴·사용량·유통기한을 서버에 저장한다. 최초 재고는 실제 등록값이며 조회만으로 가짜 수량이나 유통기한을 만들지 않는다.
- 조리 시작과 재고 차감은 같은 DB 트랜잭션에서 처리한다. 부족하면 둘 다 반영하지 않는다. 다른 주문의 동시 차감은 누적되고, 같은 주문의 재요청은 중복 차감하지 않는다.
- 재고 저장은 화면에서 읽은 전체 재고 ID·시각을 비교한다. 다른 기기나 주문에서 변경·추가한 상태를 오래된 화면이 덮어쓰지 않고 충돌을 알린 뒤 다시 조회한다. 삭제도 읽었던 전체 목록을 기준으로 검증한다.
- 공동 장바구니는 8초 주기 갱신이며 각자 담은 항목을 구분한다. 첫 담기·증가·감소·삭제를 순서대로 서버에 반영하고, 저장 실패를 성공으로 숨기지 않는다. 일반 멤버의 삭제는 본인 항목에 한정하고 전체 초기화는 호스트 권한으로 구분한다.
- 매장 식사·포장과 최대 300자의 요청사항이 주문과 함께 저장되어 POS 조회로 전달된다. 1/N은 예상 분담금 안내이며 실제 분할 결제 기능이 아니다.
- 결제 기본값은 Toss다. 모의결제는 명시적 서버 opt-in과 비운영 환경에서만 가능하며 정식 릴리스에서는 선택하지 못한다. 릴리스 백엔드 URL은 명시적 HTTPS만 허용한다.
- 선결제 매장식사는 주문당 1회의 방문 요청을 생성한다. 좌석 확보나 정확한 방문 인원을 보장하지 않는다. 확인된 주문자는 1명으로 요청하고 매장에서 인원을 확인한다. 포장·POS 현장수납은 방문 예약을 만들지 않는다.
- 결제 성공·재시도에서 주문자 카트만 한 번 정리한다. 동료 항목과 주문 이후 수정·재생성한 항목은 보존한다. 웹·모바일 성공 화면도 주문 ID에 묶인 스냅샷만 사용하며, 스냅샷이 없으면 전체 카트를 지우지 않는다.

## 핵심 원인과 수정

| 원인 | 최종 처리 |
|---|---|
| 하드닝 SQL의 CASE/END와 함수 경계가 깨짐 | 마이그레이션과 선언형 스키마 복구, 실제 DB에서 실행 검사 |
| 주문과 옵션을 따로 저장 | `create_order_with_options`가 기존 주문 RPC·옵션·불변 카트 스냅샷을 한 트랜잭션에 저장 |
| 결제 승인 재요청마다 수량 차감 | `consume_ordered_session_cart_items(p_order_id)`와 `orders.cart_consumed_at`으로 주문별 1회 처리 |
| 카트 항목 수정 시점 구분 없음 | DB가 발급한 시각·행 ID를 주문 스냅샷과 비교. 이후 수정한 행은 보수적으로 전체 보존 |
| 재고 DELETE 후 INSERT와 읽고 덮어쓰기 | 매장·재고 행 잠금, 원자적 교체/차감 RPC, 주문별 차감 원장 |
| 서버 조회 실패 뒤 캐시/시드로 덮어씀 | 서버를 유일한 원본으로 사용. 조회는 쓰기를 하지 않으며 빈 목록과 실패를 구분 |
| 주문 후 클라이언트에서도 재고 차감 | 점주 화면의 중복 차감 제거. 차감은 서버만 소유 |
| 결제 후처리 중복 구현과 오류 무시 | 공통 `paid-order-post-actions.ts`, Supabase의 반환 error 검사, 재시도 가능한 결과 표시 |
| 같은 식당 세션을 찾지 못함 | 세션 목록 응답에 winnerRestaurantId 포함 |
| 일부 UI 기능·설명 불일치 | 주문 추적의 빈 목록 접근 차단, 반응형 주문 옵션, 폴링·예약·예상 분담금의 실제 수준 표시 |

## 보안 경계

새 재고·차감 원장·카트 테이블은 RLS를 켜고 PUBLIC/anon/authenticated 직접 권한을 회수한다. 자체 JWT를 검증하는 NestJS가 service_role로 접근하는 기존 구조를 유지한다. 서비스 역할을 쓰므로 애플리케이션의 매장 소유권·멤버십 검사는 계속 필수다. 카트 메뉴명·가격은 DB에서 읽고 사용자 ID는 인증 정보에서 얻는다.

릴리스 HTTPS와 모의결제 명시적 허용 원칙을 복구했다. POS 카드 시뮬레이션도 운영에서 차단한다. 결제 금액 재계산·소유권·주문 상태·외부 승인 검증과 기존 환불 일관성 검사는 유지했다. 이미 조리 중인 결제의 동일 승인 재요청은 다시 청구하거나 상태를 되돌리지 않는다.

## 의존성

호환 범위의 lockfile 패치를 적용하고 `@nestjs/platform-express`의 Multer를 보안 패치 2.5.0으로 제한했다. proxy-addr는 2.0.8이다. `npm ci`로 재설치했다. `npm audit --omit=dev --omit=optional --json`의 운영 설치 범위 경고는 0이다. 저장소 `.npmrc`가 Firebase의 미사용 선택 SDK를 제외하므로 이 범위를 명시한다. 개발 도구를 포함하면 low/moderate 경고가 남으며 major 강제 변경으로 숨기지 않았다. 패키지 경고 수와 실제 외부 공격 가능성은 구분한다.

## 검증 기록

최종 실행 결과는 다음과 같다. 테스트 실패를 안전 기대값 완화로 해결하지 않았다. 재고의 빈 서버 응답이 캐시로 바뀌는 테스트와 서버 revision 반환 테스트는 수정 전 실패를 확인했다. 결제 초기 회귀의 수정 전 행동 검사는 Gemini가 남긴 컴파일 오류 때문에 실행하지 못했다.

- 백엔드 Jest: 36개 스위트·252개 통과.
- 실제 PostgreSQL: 4개 스위트·20개 통과. 삭제 충돌을 포함한 v2 추가 재검사 7개도 통과했다.
- Flutter 전체 테스트: 61개 통과. 추가 레이아웃 검사 2개(폭 360/390px, 글자 1.5배)도 통과.
- Flutter 정적 분석: No issues found.
- NestJS 빌드: 통과.
- Flutter debug web 빌드: 통과.
- Android debug APK 빌드: 최종 소스 기준 증분 재빌드 통과.
- 운영 설치 의존성 감사: 0개.

Docker Desktop은 이 PC에서 Linux 엔진에 연결하지 못했고 WSL 배포의 디스크 경로도 없었다. 시스템 설정이나 기존 DB를 복구·삭제하지 않았다. 대신 프로젝트 밖 도구 폴더의 PostgreSQL 18.6 Windows 바이너리로 각 테스트마다 새 임시 클러스터·loopback 임의 포트를 만들었다. 종료 시 프로세스를 중지하고 로그를 남긴다. CI는 기존 PostgreSQL 16 Docker 경로를 유지하며 신규 v2 SQL 검사와 전체 Flutter 검사를 필수로 추가했다. 운영 Supabase의 PostgreSQL 버전·PostgREST 캐시·권한은 별도 확인 대상이다.

## 남은 운영 확인과 지원 범위

브라우저 캔버스 화면 캡처는 Aside CDP 타임아웃으로 완료하지 못했다. 위젯의 좁은 화면·큰 글자 검사는 별도로 통과했다.

실제 Toss 승인·환불, 운영 Supabase 마이그레이션, EC2 배포, 실제 사용자 주문은 수행하지 않았다. 로컬 SQL·API·위젯 검사 통과와 운영 완료를 동일시하지 않는다. 두 외부 Next.js POS 저장소는 이번 범위에 포함하지 않았다. 새 필드의 외부 POS 화면 표시는 각 저장소에서 별도 통합 확인이 필요하다.

결제 이후 카트 행이 수정되면 잘못 삭제하는 것보다 해당 행 전체를 남기는 정책을 선택했다. 주문하지 않은 항목을 보존하는 대신 이미 결제한 항목이 로컬/공동 카트에 남을 수 있다. 주문내역을 기준으로 확인하고 사용자가 정리할 수 있다. 실제 그룹 대표 결제·정산·다자 분할 승인은 구현했다고 주장하지 않는다.

방문 요청은 자동 좌석 홀딩이 아니며 식당의 수동 확인이 필요하다. 예약 중복 방지는 결제 주문 ID 기반이며 일반 고객의 수동 예약 요청은 별개의 기존 API다. 재고 복원은 취소·환불만으로 임의 수행하지 않으며 이미 사용한 재료의 복원 규칙은 매장 운영 정책이 필요하다.

## 적용·롤백

운영에서는 백업과 별도 비운영 Supabase 검증 후 두 신규 마이그레이션을 순서대로 적용하고 API를 배포해야 한다. 앱/API만 먼저 배포하면 새 RPC가 없어 주문·재고 저장이 실패하므로 같은 배포 계획으로 다룬다. 이번 작업에서 운영 적용하지 않았다.

원복 시 코드와 API 계약을 함께 되돌린다. 운영 데이터를 가진 신규 테이블·열을 자동 DROP하지 않는다. 이미 차감된 재고·완료된 결제를 코드 롤백으로 재실행하지 않는다. 결제·카트 처리 원장과 주문 ID를 기준으로 대사한다.

## 도구와 검토 기록

pstack의 `tdd`, `Make Operations Idempotent`, `Prove It Works`, `Test Behavior, Not Implementation`을 읽고 적용했다. 주문 ID·처리 원장을 선택하고, 반환 상태 대신 DB 행·권한·동시성·재시도 결과를 검사하도록 결정했다. 출처는 [backnotprop/pstack](https://github.com/backnotprop/pstack), 검토한 커밋은 `4ae1636abe217c7215774bf6b2265916a5c5f648`이다. 전체 모델 설정·외부 서비스 권한을 변경하거나 사용하지 않는 모델을 실행했다고 보고하지 않았다.

Gemini가 만든 v2 변경을 보존하고 Codex가 코드 검토·보완·테스트를 수행했다. 테스트는 합성 데이터와 격리 DB로 실행했다. 사람의 운영·실기기 검증은 별도로 수행해야 한다.
