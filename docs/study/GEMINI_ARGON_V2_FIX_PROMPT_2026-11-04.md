## 3. 1단계 — 결제와 릴리스 설정 안전장치 복구

### 모의결제

`backend/src/orders/orders.service.ts`의 `assertPaymentMethodAllowed`가 `ALLOW_SIMULATED_PAYMENTS !== 'false'`로 바뀌었다. 설정 누락 시 허용된다. **정확히 'true'인 명시적 opt-in + 비운영 환경**에서만 허용하도록 복구해라. NODE_ENV='production'에서는 opt-in이어도 거부해야 한다. 환경변수 누락·빈 값·'false'·임의 문자열에서 거부하고, 거부 시 주문 RPC나 결제 부작용이 발생하지 않아야 한다.

`lib/features/payment/order_review_screen.dart`는 SIMULATE를 기본 선택하고 '원탭 간편결제(즉시 승인)'라고 표시한다. 기본은 실제 결제 흐름인 TOSS로 복구해라. 모의결제가 꼭 필요하면 개발·테스트용임을 명확히 표시하고 정식 릴리스에서는 선택할 수 없도록 해라. 클라이언트 제한은 서버 검증을 대체하지 않는다. 성공 화면도 실제 승인과 테스트 완료를 혼동시키지 마라.

### HTTPS

`lib/core/config/app_config.dart`의 release URL 검증이 URL 미지정일 때 건너뛰어지고 localhost HTTP도 허용된다. release에서는 명시적인 유효 HTTPS BACKEND_URL만 허용하고 누락·HTTP·userinfo·query·fragment가 있으면 실패시켜라. BACKEND_HOST나 기본 localhost로 우회하면 안 된다. debug/profile의 로컬 개발 경로는 유지해라. `test/app_config_test.dart`의 안전 기대값을 유지하고 BACKEND_HOST 우회도 검사해라.

## 4. 2단계 — DB 권한·재고의 데이터 보존

### 신규 테이블 권한과 스키마

`supabase/migrations/20261103000001_commercial_inventory_and_shared_cart.sql`에 추가된 `pos_inventory_items`, `session_cart_items`는 RLS와 명시적인 권한 계약이 없다. 실제 노출은 기존 기본 권한에 따라 달라지므로 운영 노출을 입증했다고 보고하지 마라.

- 현재 구조는 자체 JWT + NestJS가 service_role로 DB 접근한다. 이 구조를 고려해 두 테이블 RLS를 활성화하고 PUBLIC/anon/authenticated의 직접 권한을 회수해라. service_role에 필요한 최소 권한을 명시해라. 클라이언트 직접 접근 권한을 편의상 열지 마라.
- 애플리케이션의 매장 소유권·세션 멤버십 검증은 계속 필수다. service_role은 이를 대신하지 않는다.
- `supabase/schemas/lunchsync.sql`에 신규 컬럼·테이블·제약·권한·RPC를 함께 반영해 선언형 스키마와 마이그레이션이 어긋나지 않게 해라.
- 이미 적용된 이력이라면 과거 마이그레이션만 수정해 끝내지 말고 후속 교정 마이그레이션을 제공해라. 적용 여부는 추측하지 마라.
- 수량·가격·레시피 사용량 등에 적절한 CHECK·범위·FK·고유 제약을 두어 API 우회도 방어해라. 날짜를 문자열로 저장할지 date로 관리할지 기존 데이터를 고려해 결정해라.
- 신규 RPC의 함수 실행 권한·search_path·SECURITY INVOKER/DEFINER 선택도 검토해라. 권한 없는 역할의 직접 RPC 실행을 열지 마라.

### 재고 저장

`backend/src/pos/pos.service.ts:998`의 saveInventory는 전체 DELETE 뒤 변환/INSERT하며 오류를 무시한다. 컨트롤러는 누락된 items도 빈 배열로 처리한다.

- 필수 중첩 DTO로 배열·항목 수·문자열 길이·정수 범위·중복 ID·null 항목·잘못된 날짜 등을 전체 검증한 후에만 저장해라.
- items 필드 누락/잘못된 타입과 사용자가 명시적으로 빈 배열을 저장한 경우를 구분해라.
- 전체 교체는 한 트랜잭션/RPC에서 수행해 INSERT 오류 시 이전 재고가 그대로 남아야 한다. 동시 교체와 주문 차감의 순서도 정의해라. 실패한 뒤 삭제 데이터를 best-effort 재삽입하는 보상 방식으로 원자성을 가장하지 마라.
- DB 오류는 통제된 실패 응답으로 전달하고 민감하지 않은 오류 코드로 기록해라.

### 조리 시작과 재고 차감

`pos.service.ts:572`, `:1028`은 주문 상태를 먼저 반영한 뒤 재고를 읽고 덮어써서 동시 주문의 차감을 잃을 수 있다. 차감 실패가 숨겨지고 재시도는 이미 PREPARING이면 반환한다.

- 상태 전이와 재고 차감이 함께 성공하거나 함께 롤백되게 해라. 주문 상태 CAS·재고 행 잠금·주문 ID 기반 중복 차감 방지를 사용해라.
- 다른 두 주문이 재고 10을 각각 2씩 사용하면 최종 6이어야 한다. 같은 주문의 중복 요청은 한 번만 차감되어야 한다.
- 재고 부족/미연결 레시피/이미 취소된 주문 정책을 명시하고 임의로 0으로 덮어 성공시키지 마라.
- 취소·환불 상태와 기존 POS 상태 전이를 깨뜨리지 마라. 재고 복원 범위를 추가한다면 정확한 1회 처리와 복구 근거를 갖춰라.

## 5. 3단계 — 공동 장바구니의 권한·동기화

`backend/src/sessions/sessions.controller.ts`, `sessions.service.ts:642`, `:686` 및 `lib/features/menu/menu_screen.dart`를 함께 수정해라.

- 작성자 userId는 JWT에서만 얻고 다른 사용자를 지정하는 입력을 신뢰하지 마라.
- 필수 DTO로 menuItemId·quantity를 검증하고 메뉴명·가격은 서버의 판매 메뉴 정보에서 채워라. 선택 식당·세션 상태·멤버십도 검증해라. 0을 삭제 의미로 쓸 경우 명시적으로 정의하고 음수/소수/과도한 수량을 거부해라.
- 일반 멤버는 본인 카트 항목만 수정/삭제하게 해라. 전체 초기화가 필요하면 호스트 전용의 명확한 별도 권한·동작으로 분리해라. 멤버라는 이유로 동료 항목 전체 삭제를 허용하지 마라.
- 모든 Supabase error를 확인해 저장 실패를 정상 빈 카트로 숨기지 마라.
- 첫 담기·+·-·마지막 항목 삭제·합치기·재입장 때 로컬과 서버 상태가 일관되어야 한다. 전역 cartProvider와 세션별 DB 카트의 기준, 다른 식당 전환, 사용자 로그아웃 시 처리를 정해라.
- 폴링 또는 구독 중 현재 인증 구조와 맞는 방식을 선택해 실제 갱신을 구현해라. 폴링이라면 화면 종료 시 중단, 요청 중복 방지·간격·backoff·인증 만료 처리와 서버 throttle을 고려해라. 실시간이라고 표시하면서 입장 시 1회만 읽지 마라.
- 결제 직후 세션 전체 카트를 지우지 마라. 결제 대상 사용자·품목·수량만 정리하고 결제 도중 추가된 새 항목도 보존해라. 주문에 포함된 버전/스냅샷 등을 기준으로 처리해라.

## 6. 4단계 — 결제·예약·화면의 실제 동작 일치

### 예약

`orders.service.ts`의 tryCreatePrepaidPosReservation는 실제 좌석을 확보하지 않고, 개별 주문마다 전체 세션 인원 예약을 생성한다. Toss confirm 경로에는 연결되어 있지 않다.

- 각자 결제와 대표 결제의 실제 지원 범위를 먼저 확인해 예약의 단위를 정해라. 주문별인지 그룹별인지 일관된 ID와 인원 기준을 사용해 중복 생성되지 않게 해라.
- 실제 지원하는 결제 완료 경로에 공통 멱등 후처리를 두어라. Toss의 외부 승인과 로컬 DB를 하나의 트랜잭션이라고 가정하지 말고, 후처리 실패를 기록·재시도할 수 있게 해라. 결제 성공 후 예약 실패를 이유로 결제 자체를 실패한 것처럼 재청구하지 마라.
- 좌석 홀딩을 보장하려면 기존 예약·동시 요청을 반영하는 원자적 확보가 필요하다. 이를 이번 범위에서 안전하게 구현할 수 없다면 보장 문구를 제거하고 '방문 예약 요청, 매장 확인 필요'처럼 실제 수준으로 표시해라.
- 포장 주문에서 매장 식사용 좌석 예약이 생기지 않아야 한다.

### 미연결 주문 옵션

현재 diningType·splitCount·note는 UI에만 있고 createOrder payload에 없다. 알레르기 제외 요청처럼 보이는 입력이 실제 매장에 전달되지 않는다.

- 이번 범위에서 지원할 옵션은 검증 DTO → DB 저장 → 주문 조회 → POS 표시까지 연결하고 회귀 검사해라.
- 실제 분할 결제 계약과 정산 처리가 없다면 '1/N 결제'라고 표시하지 마라. 단순 인당 예상액 표시는 실제 결제가 전체 금액임을 명확하게 구분해라. 임의로 새로운 결제 상품을 구현하지 마라.
- 끝까지 연결하지 못하는 옵션은 제거하거나 명시적으로 비활성화해라. 선택·입력을 받으면서 조용히 버리지 마라. 지원 범위를 바꿨다면 문서에 적어라.

### 화면 회귀

- `menu_screen.dart:688`: 주문 0건·공동 카트 존재 상태에서 `_sessionOrders.first` 접근을 막아라. 주문이 있어야만 추적 버튼이 동작해야 한다.
- 다른 식당 또는 미확정 활성 세션이 있어도 바로 주문이 첫 비완료 세션으로 잘못 연결되지 않게 해라. 같은 식당의 주문 가능 세션만 재사용하거나 명시적인 새 세션 의도를 전달해라.
- `order_review_screen.dart:409`의 Row overflow를 수정하고 360~390px 모바일, 태블릿/웹, 큰 글자에서 주요 조작을 사용할 수 있게 해라. 긴 문구를 잘라 숨기는 것만으로 처리하지 마라.

## 7. 5단계 — 의존성·검증·CI

의존성 경고는 이번 v2가 만든 문제와 기존에 누적된 문제를 분리해라. `npm audit --omit=dev --json`과 실제 `npm ls` 경로·lockfile·.npmrc·배포 설치 옵션을 함께 검토해라. 감사에서 운영으로 분류돼도 실제 설치에서 제외되는 선택 의존성이 있을 수 있다.

- 검토 당시 proxy-addr 2.0.7에 critical 권고가 있었다. 해당 권고는 특정 신뢰 서브넷 설정을 전제로 하며 현재 앱은 숫자 hop 설정이다. 공격이 확인됐다고 과장하지 말고 패치와 도달성 판단을 분리해라.
- Multer 2.2.0과 업로드 경로, body-parser·@fastify/busboy 등 high 항목의 적용 조건도 확인해라.
- 호환되는 패치부터 적용하고 무분별한 `npm audit fix --force`, 도구 major 다운그레이드, broad override, 검증 없는 패키지 제거를 하지 마라. 남는 경고는 경로·조건·조치/잔여 이유를 보고해라.

필수 실행:

```powershell
# 저장소 루트
git diff --check
cmd /c flutter analyze --no-pub
cmd /c flutter test --no-pub

# backend 디렉터리
cmd /c npm test -- --runInBand
cmd /c npm run build
cmd /c npm audit --omit=dev --json
```

새 의존성 변경이 있으면 적절한 의존성 설치·lockfile 검증을 먼저 해라. 기존 backend/test/support/disposable-postgres.ts를 참고하되 현재 PostgreSQL 테스트가 새 SQL을 실제 로드하는지 확인해라. 기존 테스트 통과만으로 신규 마이그레이션 검증을 대신하지 마라.

추가해야 할 핵심 검증:

1. 모의결제 환경 조합과 주문 생성 전 거부, release URL 누락·HTTP·host 우회.
2. anon/authenticated의 테이블·RPC 직접 접근 거부, service_role의 필요한 접근 허용, 타 매장/타 세션 거부.
3. 재고 교체의 중복 ID/null/숫자 오류/DB 삽입 실패에서 이전 재고 보존.
4. 서로 다른 두 주문 동시 차감, 같은 주문 중복 요청, 차감 장애 시 상태·재고 함께 롤백.
5. 두 사용자 카트의 추가/감소/삭제/갱신, 동료 항목 보존, 쓰기 실패 표시, 결제 중 추가분 보존.
6. 주문 없는 카트의 추적 버튼, 다른 식당 활성 세션이 있는 바로 주문, 작은 화면·큰 글자.
7. 실제 지원하는 결제 승인 경로의 예약 1회 처리, 포장 예약 제외, 예약 후처리 실패·재시도에서 중복 청구/중복 예약 없음.

테스트는 의미 있는 실패·권한·경쟁 상태를 검증해라. 구현 함수 호출 횟수만 맞추는 테스트로 대체하지 마라. DB mock만으로 원자성과 동시성을 입증했다고 보고하지 마라. 테스트용 DB/Docker가 없으면 미실행 사유와 남은 검사 절차를 적어라.

`.github/workflows/verify.yml`의 Flutter 검사는 현재 widget_test.dart만 실행한다. 전체 Flutter 회귀 검사가 필수가 되도록 맞춰라. SQL 역할·트랜잭션 검사를 CI에서 실행할 수 있게 구성하되 production 배포나 원격 DB 변경을 연결하지 마라.

## 8. 완료 보고 방식

단계별 검증을 수행하며 작업하고, 마지막에 다음을 보고해라.
