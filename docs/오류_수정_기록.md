## 1. RenderFlex overflow 다수

### 오류 내용

실행 직후 콘솔에 overflow 예외가 11건 연속 발생:

```
A RenderFlex overflowed by 82 pixels on the right.
  Row Row:.../lib/features/auth/login_screen.dart:326:9
  constraints: BoxConstraints(w=110.0, 0.0<=h<=Infinity)
Another exception was thrown: A RenderFlex overflowed by 24 pixels on the right.
Another exception was thrown: A RenderFlex overflowed by 6.0 pixels on the bottom.
... (bottom 64/64/52/39, right 105/88 등)
```

### 원인

이 앱은 **모바일(Flutter) 기준 설계**(디자인 시스템도 모바일 폭 기준)인데
`flutter run -d chrome` 로 **데스크톱 Chrome 의 넓은/불규칙 뷰포트**에 띄우면서
다음이 겹쳤다:

- 웹 첫 프레임에서 브라우저가 실제 창 크기를 보고하기 전 매우 좁은
  캔버스(예: 폭 110px)로 1회 레이아웃 → `login_screen.dart:326`
  회원가입 Row 등 가로 위젯이 공간 부족
- 모바일 고정 높이 레이아웃이 데스크톱 뷰포트 높이와 불일치 → 세로 overflow

### 수정 내용

`lib/main.dart` — 웹일 때만 앱 전체를 폰 크기 프레임으로 고정.
`MaterialApp.builder` 로 Navigator 를 감싸 **모든 화면·다이얼로그·스낵바**에
일괄 적용. 내부 `MediaQuery.size` 도 프레임 크기(420 × 가용높이)로 덮어써
각 화면이 모바일 기준으로 레이아웃되게 함. `kIsWeb` 가드로 네이티브
모바일 빌드에는 영향 없음.

- `import 'package:flutter/foundation.dart' show kIsWeb;` 추가
- `MaterialApp` 에 `builder: (context, child) => _WebFrame(child: child)` 추가
- `_WebFrame` 위젯 신규: `LayoutBuilder` → 폭 420 고정 `SizedBox` + `ClipRect`
  + `MediaQuery` size 오버라이드, 창이 더 넓으면 중앙 정렬·바깥 배경
  (`0xFFE9ECF1`), 더 좁으면 `FittedBox` 축소

> 디자인 시스템(`docs/LUNCHSYNC_CODE_GUIDE.md` §3)·아키텍처 원칙 변경 없음.
> UI 셸만 추가. 모바일 폭 420 은 디자인 시스템 기준 폭과 일치.

## 2. FCM service worker 등록 실패

### 오류 내용

```
[FcmService] registerToken 예외 (무시): [firebase_messaging/failed-service-worker-registration]
Messaging: We are unable to register the default service worker.
Failed to register a ServiceWorker ... script ('http://localhost:8080/firebase-messaging-sw.js'):
The script has an unsupported MIME type ('text/html').
```

### 원인

`web/firebase-messaging-sw.js` 파일이 없어 dev 서버가 SPA fallback 으로
`index.html`(MIME `text/html`)을 반환 → 브라우저가 service worker 스크립트로
거부 → `firebase_messaging` 웹 플러그인이 등록 실패 → `FcmService` 가
예외를 잡아 `debugPrint` 로 콘솔에 출력.

`docs/LUNCHSYNC_AUTH_DECISION.md` 기준 **Firebase 는 캡스톤에서 테스트/비활성**
(백엔드도 `FIREBASE_PROJECT_ID 미설정 — Firebase Phone Auth 비활성` 로그).
즉 웹 푸시는 캡스톤 범위 밖.

### 수정 내용

- `lib/services/fcm_service.dart` — `registerToken()` 진입부에 `kIsWeb` 가드
  추가. 웹에서는 등록을 **조용히 건너뜀**(예외·로그 미발생). 네이티브
  모바일은 그대로 동작.
- `web/firebase-messaging-sw.js` 신규 — 방어용 no-op service worker.
  혹시라도 브라우저가 이 경로를 요청하면 SPA fallback(text/html) 대신
  정상 JavaScript(MIME) 가 응답되도록. 운영 전환 시 firebase 설정을
  채워 실제 백그라운드 핸들러로 확장하는 주석 포함.

## 3. Noto fonts 누락 글자 경고

### 오류 내용

```
Could not find a set of Noto fonts to display all missing characters.
Please add a font asset for the missing characters.
```

### 원인

테마가 `GoogleFonts.notoSans` / `GoogleFonts.notoSansTextTheme()` 사용.
`Noto Sans`(베이스)는 **라틴 전용 글리프**라 **한글이 없음**. 한글 텍스트
렌더 시 CanvasKit 이 폴백 폰트를 찾다 실패 → 경고 출력.

`docs/LUNCHSYNC_CODE_GUIDE.md` §3 의 `app_text_styles.dart` 설명은
"Noto Sans 폰트, 한글 최적화" 의도였으나 실제로는 한글 미포함 패밀리가
지정돼 의도와 불일치.

### 수정 내용

한글 포함 패밀리 `Noto Sans KR` 로 교체 (문서의 "한글 최적화" 의도와 일치):

- `lib/core/theme/app_text_styles.dart` — `GoogleFonts.notoSans(...)`
  → `GoogleFonts.notoSansKr(...)`
- `lib/core/theme/app_theme.dart` — `GoogleFonts.notoSansTextTheme()`
  → `GoogleFonts.notoSansKrTextTheme()`

> 코드 내 이모지/특수기호 사용은 grep 결과 0건 — 한글 글리프 누락이 유일 원인.

## 4. 429 ThrottlerException — 폴링·주문·결제 전면 차단 (치명)

### 오류 내용

재실행 검증 중 발견. 콘솔에 다음이 폭주:

```
[VotesApiService] getVotes 실패: 429 body={"statusCode":429,"message":"ThrottlerException: Too Many Requests"}
(투표 폴링마다 무한 반복)
```

### 원인 (근본)

`@nestjs/throttler` 는 `ThrottlerModule.forRoot([...])` 에 등록된 **모든 명명
throttler 를 모든 라우트에 동시 적용**한다. `backend/src/app.module.ts` 가
`default`(1000/분) 외에 `auth`(30/분), `signup`(**30/시간**) 까지 전역 등록 →
`signup` 의 시간당 30회 제한이 **투표 폴링·주문·결제·리뷰 등 전 API 에 적용**.

`docs/LUNCHSYNC_SPECIFICATION.md` 의 **3초 폴링** 설계상 단일 사용자가 ~90초
만에 시간당 30회를 초과 → 이후 1시간 동안 **모든 요청 429**. 결제(`POST
/orders`, `POST /payments/confirm`)도 동일하게 막힘.

> Throttler 는 2026-05-15 커밋(`95b00e4`/`d2774c9` 계열)에서 추가됨 →
> "예전엔 토스 결제가 바로 됐는데 지금 안 됨" 증상의 직접 원인으로 추정.
> auth.controller 의 `@Throttle({ auth: ... })` 는 그 라우트의 'auth' 명명
> throttler 만 오버라이드할 뿐, 다른 라우트의 전역 'signup' 적용은 못 막음.

### 수정 내용 (NestJS 표준 패턴)

전역에는 넉넉한 `default` 1개만 두고, auth/signup 브루트포스 강화는 해당
라우트에서 `@Throttle({ default: { ... } })` 로 그 라우트에만 한정:

- `backend/src/app.module.ts` — `forRoot` 를 `[{ name:'default', ttl:60_000,
  limit:1000 }]` 1개로 축소 (`auth`/`signup` 명명 제거)
- `backend/src/auth/auth.controller.ts` — `kakao`/`signup/email`/`login/email`
  의 `@Throttle({ auth|signup: ... })` → `@Throttle({ default: { limit:30,
  ttl:60_000 } })`(로그인) / `{ limit:30, ttl:3_600_000 }`(가입)
- `backend/src/pos/pos-auth.controller.ts` — POS 로그인 동일하게 default 오버라이드

> 결과: 폴링/주문/결제/리뷰는 전역 1000/분만 적용(3초 폴링 안전), auth/signup
> 라우트는 여전히 분당 30 / 시간당 30 으로 브루트포스 방어 유지.
> docs 의 폴링 아키텍처와 양립.

### 알아둘 점 (오류 아님, 정상 동작)

- `flutter run -d chrome` 개발 서버는 `web/` 루트의 임의 파일을 서빙하지
  않아 `GET /firebase-messaging-sw.js` 가 **404(text/plain)** 로 응답된다.
  → **무해**: #2 의 1차 방어(`kIsWeb` 가드)로 웹에서 FCM 등록을 아예
  건너뛰므로 브라우저가 이 SW 를 요청하지 않는다. 콘솔 오류 0건.
  → `web/firebase-messaging-sw.js`(no-op) 파일 자체는 정상 존재하며,
  운영 `flutter build web` 빌드에서는 build 루트로 복사돼 올바른 MIME 로
  서빙된다. 개발 서버 한정 동작이라 코드 수정 불필요.
- `[AuthApiService] kakao 상태: 201` 및 `FIREBASE_PROJECT_ID 미설정 —
  Firebase Phone Auth 비활성` 은 설계상 정상 로그(오류 아님).
- 카카오 OAuth 는 자동화 불가 구간이라 로그인 이후 화면(홈/폴링)은
  수동 시연으로 확인 필요. 단, #4 폴링 차단은 백엔드 throttler 직접
  부하 테스트로 해소를 독립 검증함.

**결론:** 백엔드·웹 동시 실행 시 코드 수정이 필요한 신규 오류 없음.
기존 4개 수정 사항 모두 라이브 환경에서 재현·해소 확인 완료.
